# Utils

## Metadata Resolution

Generate comprehensive Next.js metadata from Sanity content, including SEO tags, Open Graph images, and internationalization support.

```tsx
// In your page or layout
import {resolveSanityMetadata} from "./lib/sanity";
import {loadPage} from "./lib/sanity/queries";

export async function generateMetadata(
  {params}: {params: Promise<{slug: string; locale: string}>},
  parentPromise: Promise<ResolvedMetadata>,
) {
  const parent = await parentPromise;
  const {slug, locale} = await params;

  const data = await loadPage({slug, locale});

  if (!data) return {};

  return resolveSanityMetadata({
    parent,
    title: data.title,
    seo: data.seo,
    pathname: data.pathname,
    locale,
    translations: data.translations,
  });
}
```

### ResolveSanityMetadata Props

| Prop           | Type                        | Description                               |
| -------------- | --------------------------- | ----------------------------------------- |
| `parent`       | `ResolvedMetadata`          | Parent metadata from Next.js              |
| `title`        | `string` (optional)         | Page title                                |
| `seo`          | `object` (optional)         | SEO configuration object                  |
| `pathname`     | `string\|object` (optional) | Page pathname or slug object              |
| `locale`       | `string` (optional)         | Current locale                            |
| `translations` | `array` (optional)          | Array of translation objects for hreflang |

## Redirects

Handle redirects stored in the first `settings` document's `redirects` array. By default, lookup uses only the request pathname and accepts the existing leading/trailing slash variations.

Enable exact query-string matching in your existing client setup:

```tsx
import {initSanity} from "@tinloof/sanity-next/client";

export const {redirectIfNeeded} = initSanity({
  redirects: {matchQueryString: true},
});
```

For exact matching against the original incoming query string, also disable Next.js proxy URL normalization in your existing Next configuration:

```ts
// next.config.ts
const nextConfig = {
  skipProxyUrlNormalize: true,
};
export default nextConfig;
```

Without this flag, Next.js can reserialize the query before Kit receives it, for example changing `%20` to `+` or regrouping repeated keys. Kit matches the `NextRequest` it receives and cannot recover the original spelling afterward. Review [Next.js proxy normalization and trailing-slash flags](https://nextjs.org/docs/app/api-reference/file-conventions/proxy#advanced-proxy-flags) when enabling this option. Next's own trailing-slash redirect can also run before the proxy; disable it only if your application handles that policy itself.

Return the response from your proxy before continuing with locale rewrites or other routing:

```tsx
// proxy.ts
import type {NextRequest} from "next/server";
import {redirectIfNeeded} from "@/lib/sanity";

export async function proxy(request: NextRequest) {
  const redirect = await redirectIfNeeded({request});
  if (redirect) return redirect;
  // Continue with other routing when no redirect matches.
}
```

With `matchQueryString: true`, `/jobs?gh_jid=123` first looks for that complete query string. If no rule matches, it falls back to `/jobs`. Query parameter order, duplicates, case, and encoding are literal: extra parameters or `%20` instead of `+` can cause path fallback. Slash variations apply only to the pathname, so `/jobs/?gh_jid=123` can match `/jobs?gh_jid=123`. Query values containing slashes are unchanged. An empty query string uses the path lookup only. This does not add regex, wildcard, or subset matching.

The first matching array entry wins within each lookup. Query-specific rules take priority over path rules regardless of array order. Incoming query parameters are discarded unless the matched rule sets `keepQueryParameters: true`. Destination query strings and fragments are preserved through URL resolution. Permanent redirects return **301** and temporary redirects return **302**. Every lookup uses `perspective: "published"` and `stega: false`. An unmatched query adds one lookup before path fallback; requests without a query still need only one.

Set **Keep query parameters** on an individual Studio redirect to forward incoming query values. The stored field is `keepQueryParameters?: boolean`, defaulting to false. Missing or false retains the existing behavior; no global configuration is needed. Destination query keys take priority, including empty values. All repeated incoming values for other keys are appended in order; destination fragments and absolute URLs are retained. Copied parameters use standard URL query serialization, so their encoding may change while their values are preserved.

For example, `{source: "/old", destination: "/new?campaign=fixed#form", permanent: true, keepQueryParameters: true}` redirects `/old?campaign=incoming&tag=a&tag=b` to `/new?campaign=fixed&tag=a&tag=b#form`. This works with both exact-query hits and path fallback, using only the matched rule's flag.

Omit `redirects`, pass `{}`, or set `matchQueryString: false` to retain path-only behavior. The same options work with i18n; lookup uses the incoming pathname before your locale rewrite. The existing Studio `redirectsSchema` already accepts sources such as `/jobs?gh_jid=123` without a schema migration.

For redirects stored elsewhere, set `redirects.query`:

```tsx
export const {redirectIfNeeded} = initSanity({
  redirects: {
    matchQueryString: true,
    query: '*[_type == "siteSettings"][0].rules[source in $paths][0]',
  },
});
```

A custom query receives `$paths: string[]` and must return `{source: string, destination: string, permanent: boolean}` or `null`. The same query runs for each lookup: query-bearing path variations first, then path-only variations if necessary. Existing `$paths` queries need no additional parameters. If a custom query projects fields, include `keepQueryParameters` in the returned redirect to enable forwarding; omitting it keeps query parameters discarded.

`initSanityUtils` and `initSanityI18nUtils` from `@tinloof/sanity-next/utils` also accept `redirects`. Direct `getRedirect` and `redirectIfNeeded` calls accept `matchQueryString` and `query` alongside their existing arguments. With direct `getRedirect`, include the query in `source`, for example `getRedirect({source: "/jobs?gh_jid=123", sanityFetch, matchQueryString: true})`.

## Sitemap Generation

`initSanity()` returns `generateSitemap()` for both single-language and i18n configurations. Export it from your Next.js sitemap route:

```tsx
// app/sitemap.ts
export {generateSitemap as default} from "@/sanity";
```

By default, documents must have `seo.indexable` enabled and either a `pathname.current` or `_type == "home"`. The helpers use `_updatedAt` for `lastModified`. Fetches always use `perspective: "published"` and `stega: false`.

### Custom Query

Set `sitemap.query` in your existing `initSanity` configuration to replace the selection and projection. URL generation still uses the configured `baseUrl`. Omitting `sitemap`, passing `sitemap: {}`, or omitting its `query` keeps the default query.

```tsx
// sanity/index.ts
import {initSanity} from "@tinloof/sanity-next";
import {defineQuery} from "next-sanity";

export const {generateSitemap} = initSanity({
  baseUrl: "https://example.com",
  sitemap: {
    query: defineQuery(`*[
      _type in ["legalPage"] &&
      coalesce(noIndex, false) == false &&
      defined(pathname.current)
    ] {
      _type,
      "pathname": pathname.current,
      "lastModified": coalesce(lastUpdatedAt, publishedAt)
    }`),
  },
});
```

This example includes only `legalPage` documents whose `noIndex` is false or missing. Only allow document types whose frontend routes exist. For an application with no document-backed routes yet, use `_type in []` until those routes are implemented.

The date projection is a consumer choice: it prefers an editorial update date, then a publication date. If both are missing, the sitemap omits the XML `lastmod` element. The package's default `_updatedAt` policy is unchanged.

The query must return an array of objects with this shape:

```ts
{
  _type: string;
  pathname: string | null;
  lastModified?: string | null;
}
```

Use site-relative paths beginning with `/`. `_type == "home"` keeps the existing special handling for the site root; otherwise the single-language helper appends `pathname` to `baseUrl` as provided. Return valid date strings, or omit `lastModified`/return null to leave out the date.

The helper supplies `$homeType` as `"home"`. The query does not have to use it. No additional query parameters are configurable.

### Custom i18n Query

With `i18n` configured, the same `sitemap.query` option replaces the i18n query. It runs once per configured locale and receives `$locale` as well as `$homeType`.

```tsx
import {initSanity} from "@tinloof/sanity-next";
import {defineQuery} from "next-sanity";

export const {generateSitemap} = initSanity({
  baseUrl: "https://example.com",
  i18n: {
    defaultLocaleId: "en",
    locales: [
      {id: "en", title: "English"},
      {id: "fr", title: "French"},
    ],
  },
  sitemap: {
    query: defineQuery(`*[
      _type in ["legalPage"] &&
      coalesce(noIndex, false) == false &&
      defined(pathname.current) && locale == $locale
    ] {
      _type,
      locale,
      "pathname": pathname.current,
      "lastModified": coalesce(lastUpdatedAt, publishedAt),
      "translations": (*[
        _type == "translation.metadata" && references(^._id)
      ].translations[].value->)[
        _type in ["legalPage"] &&
        coalesce(noIndex, false) == false && defined(pathname.current)
      ] {
        "pathname": pathname.current,
        locale
      }
    }`),
  },
});
```

Each route must also return `locale: string` matching the requested `$locale` and `translations: {pathname: string | null; locale: string}[]`. Return an empty translations array when there are no alternatives. A custom query that returns a non-array result, omits these fields, or returns a different locale throws an error instead of producing an incorrect sitemap. Filter translations to eligible, implemented routes as well.

The existing locale prefixes, language alternates, and `x-default` calculation are unchanged. A single-language projection cannot be reused unchanged for i18n.

### Direct Utilities

`initSanityUtils` and `initSanityI18nUtils` from `@tinloof/sanity-next/utils` also accept `sitemap.query`. When calling `generateSanitySitemap` or `generateSanityI18nSitemap` directly, pass the override as `query` alongside the existing `sanityFetch`, `websiteBaseURL`, and, for i18n, `i18n` arguments. Omitting it keeps the corresponding default query.
